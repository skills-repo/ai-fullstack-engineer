# 浏览器操作横切 playbook（browser-ops playbook）

> 无论选哪个方案（视觉驱动 / 选择器 / CDP / MCP），登录态、文件上传、动态表单、人机验证、合规这五关都要过。
> 路由决策见 [SKILL.md](../SKILL.md)；本文只写决策方法论与 SOP，不重复子技能命令。

## 1. 登录态管理三模式对比

| 模式 | 机制 | 登录态持久性 | 风控友好度 | 适用 | 踩坑 |
|------|------|-------------|-----------|------|------|
| **storage_state** | 导出/导入 cookie+localStorage JSON | 中（有过期时间） | 中 | 无头/CI、可跨机迁移 | 过期需人重新扫码；敏感文件不入库 |
| **持久 profile（user-data-dir）** | 完整浏览器用户目录 | 高（含指纹、扩展） | **高**（最接近真人） | 长期复用、风控敏感站点 | 同一目录单实例；并行要多目录 |
| **CDP / Bridge 接管真实浏览器** | 接管用户已开的 Chrome | **最高**（全部登录态与指纹） | 最高 | 已登录的重站点、需要人旁边守着的流程 | 需开远程调试（9222）或装扩展；只做用户授权动作 |

**选型口诀**：一次性任务用方案自带 session；要「保号」用持久 profile；要「人机协作」用 CDP 接管。
接管用户真实浏览器等于持有其登录态——**只做用户明确要求的操作**。

## 2. 文件上传（最小授权原则）

- Playwright CLI：`file chooser` 事件处理 / `upload` 命令
- MCP：`browser_file_upload` / `browser_drop`
- Midscene 视觉驱动：`act` 必须显式传 `--file-chooser-allowed-dir`，且**只给最小必要目录**——绝不放项目根或家目录（防 Agent 拿错文件上传）
- Bridge 模式上传前检查扩展「允许访问文件网址」权限

## 3. 复杂动态表单策略（电商发布页类）

电商发布页的难点：类目树自研组件、属性随类目动态渲染、SKU 矩阵编辑器、富文本详情、批量图片上传。

**内容包驱动**（核心方法）：

```text
内容包（结构化 JSON，人/AI 预先整理好）
  { 类目路径, 标题, 属性映射, 价格, 库存, 图集清单, 详情文本, 运费模板 }
     ↓ 逐字段映射到表单项
执行层（任一方案）按内容包填充 → 填到【预览】为止
     ↓
人工节点：核对预览 → 人点「发布」
```

三条铁律：
1. **填充到预览为止，发布/提交按钮永远人点**——消灭错价、错类目的灾难性误发布
2. 内容包字段名对齐表单结构，失败时人可按内容包**手动手填**（自动化不是唯一路径）
3. 类目/属性规格是复用资产：换执行方案（CLI↔MCP）时内容层原样保留

**属性规格来源提示**：官方开放平台的类目属性接口（如淘宝 `itemprops.get`）就是动态表单的权威 schema，UI 自动化同样要用它，不要靠猜。

## 4. 人机验证人工兜底 SOP

```text
检测到滑块/验证码/风控页
  → 立即暂停自动化（不要重试、不要伪装）
  → 通知人：「请手动完成验证」
  → 人操作完成后截图/快照确认页面恢复
  → 继续原流程
```

- 绝不自动绕过；不安装 stealth/anti-detect 类工具（见 §5）
- 验证频繁出现 = 行为特征已异常：降频、拉大步骤间隔、换拟人节奏，而不是对抗
- 登录态突然失效属正常：回到 §1 重新建立，不写「保活 hack」

## 5. 平台 ToS 合规红线

- 浏览器自动化普遍处于平台 ToS 灰色地带：**如实告知用户风险**，把选择权留给人
- 行为准则：低频、拟人节奏、真实内容、单账号小量；**不做**批量铺货、群控、刷量
- **不编写**：验证码绕过、指纹伪造、风控对抗、协议逆向类内容——组织内技能一律不收录此类能力
- 对抗类社区技能（stealth / anti-detect / invisible browser）高安装量也不纳入，记录为已排除信号

## 6. 故障降级路径

| 故障 | 降级动作 |
|------|---------|
| 选择器/快照 ref 失效（页面改版） | 换视觉驱动方案（Midscene）；或按内容包人工手填 |
| 视觉定位漂移 | 加 `--deep-locate`/`--deep-think`；仍漂移换选择器方案 |
| MCP 工具不可用/超时 | 回落 CLI 直跑（Playwright CLI / Midscene） |
| 登录态丢失 | 人重新登录；检查是否 profile 冲突（单实例限制） |
| 风控拦截 | §4 SOP；必要时整单转人工 |

### 3.1 已踩过的六个具体坑（2026-11-05 淘宝发布页实测）

1. **可见性判断别用 `offsetParent`**。`position:fixed` 的元素（对话框、下拉浮层）`offsetParent` 恒为 `null`，
   用它过滤会把「明明开着」的对话框判成不存在，进而误判"功能不可用"。改用
   `getBoundingClientRect()` 尺寸 + `getComputedStyle().display/visibility/opacity`。
2. **`locator("[class*=X]").filter({ hasText: 目标名 })` 会匹配到整块容器**。网格里每个卡片都含文件名，
   祖先容器也含，`.first()` 于是永远拿到网格根节点 → 点到的永远是第一张缩略图。表现是"操作成功但结果不对"。
   正确做法：从**文本节点**出发回溯到卡片本体（`getByText(name).locator("xpath=ancestor::*[contains(@class,'卡片类名')][1]/descendant::img[1]")`），
   注意最近的祖先可能只是标题 div（里面没有 img），要按卡片类名而不是通用前缀取。
3. **面板没真开时 `frames()` 会返回遗留的隐藏 iframe**。对着它点「确定」，坐标会落到主文档同位置的
   **提交按钮**上，造成误提交。操作前必须确认 iframe 内 `body.innerText` 有实际内容，而不只是"存在这个 frame"。
4. **自研下拉的开关是 toggle**。上一轮遗留的浮层还在时再点一次会把它关掉；重试逻辑必须是
   "查一次 → 没开才点 → 再查"，不能"点一次 → 等固定时间 → 假定已开"。
5. **坐标点击前重算 rect**。`scrollIntoView()` 之后立刻取的 rect 可能仍是滚动中的值；
   且页面一旦导航/重排，旧坐标会点到完全无关的控件。要么每次操作前重新定位，要么用 locator 自带滚动。
6. **"点了没生效"是常态**：一切成功判定以**回读**为准（槽位是否真有图、控件值是否变成目标串、
   类目文本是否切换），绝不用 click 的返回值或"无异常"当成功。

### 3.2 表单里"必填"的两种词形陷阱

同一字段可能是枚举型也可能是自由文本型，填错服务端直接判空且不告诉你为什么：

- **枚举型**（如分辨率只有 1080p/1440P/2160p/4320P/720p）：写 `3840x2160` 这种"看起来更精确"的自由文本会被判空，
  必须点选项。
- **需规范词形的文本型**（如生产企业要 `索尼（Sony Interactive Entertainment）` 这种中英全称）：
  原生 value setter + `input/change` 事件不生效，要用真实键盘事件（`pressSequentially` + `Tab` 触发校验）。
- 判型办法：先点开下拉看有没有候选列表；有就是枚举，必须点选；显示"无选项，请输入"才可按文本填。

### 3.3 类目/属性切换类操作的固定流程

改类目会连带重置属性、甚至重置"宝贝类型"这类单选。安全序列：

```text
选目标叶子 → 对话框内补齐它要求的品牌/型号（否则「确定」恒 disabled）
→ 点确定 → 处理二次确认（"可能导致已填写内容丢失"）
→ 回读类目文本确认已切换 → 重新填该叶必填属性 → 回读宝贝类型等单选是否被重置 → 再提交
```

叶子归属不要靠猜：用平台自己的类目预测接口/页面（输入产品名看它给哪个候选），
比按搜索结果第一个候选点进去可靠得多——第一个候选常常是配件叶。

### 3.4 状态取数分三层：服务端快照 > 派生值 > DOM input（2026-11-06 淘宝发布页实测）

「页面显示 99，提交后落库 0」这类事故，根因是拿 DOM 当事实。按可靠性排序取数：

1. **服务端快照**：很多表单页会把初值注入成全局对象（淘宝发布页是 `window.Json.models.formValues`，
   由脚本标签注入、不随输入变化）。重新加载页面后读它，才是「线上现在是什么」。
   结构化字段（数组里每个 SKU 的价/量/编码/图/上架状态）比抓 DOM 表格稳得多。
2. **派生值**：React 受控表单里，「总库存 = Σ各档数量」这种汇总值是状态真的更新了的证据；
   逐格填完必须看汇总，不能只看逐格回读。
3. **DOM input.value**：只当操作过程反馈。`fill()` 不触发 React 提交时它就是假的（典型表现：
   最后一行的值停在 DOM、状态里没有）。
4. **单选/复选控件的「选中」也别只看 class**：Next/Fusion 一类组件把 `aria-checked` 挂在
   `<label>` 上、文字挂在外层节点，`.innerText` 可能是空串——判态用 `aria-checked`/`input:checked`，
   取文字用它的宿主行容器，两者分别取再拼。

## 8. 现场收尾：谁打开谁关闭（2026-11-06 用户明确反馈后固化）

CDP 接管的是**用户看得见的浏览器窗口**，和本机无头跑不一样：脚本 `newPage()` 出来的标签页
**不会因为断开连接而消失**，用户下次打开看到的是我们工作现场。一夜堆 20+ 个页面被投诉过一次，
所以收尾和取数一样是任务的一部分。

1. **规矩**：每个工具对自己 `newPage()` 出来的页面负责，跑完（含 `--dry`、含报错路径）关掉；
   **复用了用户/别的脚本已经开着的页面则不要关**——那是别人的现场。
   代码上就是 `let openedByUs = false` + `finally` 里按标志关。
2. **`process.exit()` 会跳过 `finally`**：提前退出的分支（dry-run、校验失败）必须自己关页面再退，
   否则等于没写收尾。
3. **一次任务结束时清点**：`node tools/taobao-publish/tabs.mjs`（只列）→ `--close`（收自动化页面）。
   `--close` 有保护：**不会把标签页关到剩 0 个**。
4. ⚠️ **关到 0 个标签页 = 自己把 CDP 门锁上**：Chrome 一个页面都不剩时，
   `chromium.connectOverCDP()` 报 `Browser context management is not supported`，
   之后所有工具全部连不上（`/json/version` 依然是通的，容易被误判成端口坏了）。
   恢复：`curl -X PUT "http://127.0.0.1:9222/json/new?https://myseller.taobao.com/home.htm/QnHome"`
   （Chrome 111+ 该端点只收 **PUT**，GET 会 405），或者直接让用户在窗口里开一个标签页。
5. 诊断顺序：连不上先 `curl /json` 看 `targets` 数量——**0 个就是被关光了**，不是端口/登录问题。
